## バージョン番号の仕様

```
version: X.Y.Z+N
         ↑ ↑ ↑  ↑
         │ │ │  └── ビルド番号（+N）: リリースのたびに +1
         │ │ └───── パッチ（バグ修正のみ）
         │ └─────── マイナー（新機能追加）
         └───────── メジャー（大規模変更）
```

| バージョン例 | 使いどころ |
|------------|----------|
| `2.2.1+7` | バグ修正のみ |
| `2.3.0+7` | 新機能追加 |
| `3.0.0+7` | 大規模リニューアル |

## リリース前チェック（バックエンドのデプロイ漏れ確認）

**アプリのビルドより先に、バックエンド側のデプロイ漏れを確認する。**
アプリだけ新しくしてもFunctionsやルールが古いままだと、リリース後に不整合が起きる。

### ① Cloud Functions

デプロイ済みかは**推測せず**、実際の更新時刻とコミット時刻を**UTCに揃えて**比較する。

```bash
# 本番の最終デプロイ時刻（新しい順）
gcloud functions list --project=my-character-app --format="value(name,updateTime)" | sort -k2 -r | head -5

# shared/functions の最終コミット時刻（UTC）
TZ=UTC git log -1 --pretty=format:"%h %cd %s" --date=format-local:"%Y-%m-%dT%H:%M:%SZ" -- shared/functions/
```

> `git log --date=format:` は**コミット自身のTZ（JST）**で出るため誤読しやすい。
> UTCで見るには `TZ=UTC` と `--date=format-local:` を併用する。

コミットのほうが新しければ未デプロイ。**変更したファイルを使っている関数だけ**デプロイする。

```bash
firebase deploy --only functions:関数名 --project my-character-app
# 例: firebase deploy --only functions:scheduledDiaryGeneration --project my-character-app
```

> デプロイしてからコミットした場合は時刻が逆転して見える。判断に迷ったら
> どのコミットの内容をデプロイしたかで確認する。

### ② Firestore セキュリティルール

`firestore.rules` は**本番の内容をAPIから取得できない**（Functionsと違い更新時刻が見られない）。
変更したら必ずデプロイし、記録を残す。

```bash
TZ=UTC git log -1 --pretty=format:"%h %cd %s" --date=format-local:"%Y-%m-%dT%H:%M:%SZ" -- firestore.rules
firebase deploy --only firestore:rules --project my-character-app
```

現在の本番ルールは [Firestore ルール画面](https://console.firebase.google.com/project/my-character-app/firestore/rules) で確認できる。

### ③ 配布ページ（`dl/`）

共有テキストのURLが指す静的ページ。内容を変えたときだけデプロイする。

```bash
TZ=UTC git log -1 --pretty=format:"%h %cd %s" --date=format-local:"%Y-%m-%dT%H:%M:%SZ" -- dl/
firebase deploy --only hosting:dariasapp --project my-character-app
```

## ストア用スクリーンショット

**`画像/` は `.gitignore` で除外している**（素材が500MB超のため）。ローカルにしか無いので消さないこと。

| もの | パス |
|---|---|
| 成果物（提出するファイル） | `画像/ストア画像/iPhone/` `iPad/` |
| 生成スクリプト | `画像/ストア画像/生成スクリプト/` |
| 素材スクショ | `画像/画面スクショ/<日付>/` |

サイズは iPhone 1242x2688（6.5インチ）/ iPad 2064x2752（13インチ）。紫グラデ＋白見出し＋端末モックのテンプレートを Pillow で合成している。

```bash
cd 画像/ストア画像/生成スクリプト
python3 make_cover.py        # 1枚目（素材合成）
python3 make_shots.py        # iPhone 2〜7枚目
python3 make_ipad_cover.py
python3 make_ipad_shots.py   # iPad 2〜7枚目
```

コピーと素材の対応は各スクリプトの `SCREENS` に並んでいる。素材フォルダは `shot_dir` で画面ごとに切り替えられる。

### UIを変えたら素材を撮り直す（重要）

**見出しのテキストを直すだけでは足りない。** 実画面のスクショを使っているため、削除した機能がタブバーや画面内の文言として残り続ける。

2026-09-24 に冒険機能の痕跡を除去したときは、次の4箇所に散らばっていた。

1. 1枚目の見出し「AI × 性格診断 × 自分会議 × 冒険」
2. 1枚目に合成していた**敵モンスター画像**（アセットはリポジトリから削除済みで、スクリプトが実行不能になっていた）
3. **ボトムナビの「冒険」タブ**（実画面のスクショに写り込み）
4. **日記の本文**「冒険で『完璧主義』を克服した」

作り直したら**全枚を目視で確認する**。見出し・タブバー・画面内の文言の3箇所を見る。

### 素材の撮り方

iOSシミュレータで撮る（`xcrun simctl io <udid> screenshot out.png`）。

- 日記に「今日やったこと」を載せたいなら、**その日にチャットしてから23:50の自動生成を待つ**
- 日本語入力は `xcrun simctl pbcopy <udid>` → 入力欄をタップ → `Cmd+V` → 「ペーストを許可」
- **画面の操作は idb で行う（iPad・iPhone 共通）。** iPad シミュレータは `osascript` の `click at` も `cliclick` も通らないが、idb はマウスを使わずシミュレータに直接タップを送るので通る（2026-09-26 に確認）

  ```bash
  IDB=~/Library/Python/3.11/bin/idb
  U=<シミュレータのUDID>              # xcrun simctl list devices で確認
  $IDB ui describe-all --udid $U     # 画面の部品と位置（ポイント単位）を一覧する
  $IDB ui tap <x> <y> --udid $U      # 位置はポイント単位（describe-all の frame の中心を使う）
  $IDB ui swipe <x1> <y1> <x2> <y2> --udid $U
  $IDB ui text "文字" --udid $U        # 英数字のみ。日本語は上の pbcopy → Cmd+V を使う
  ```

  入れ方（初回のみ）: `brew tap facebook/fb && brew trust --formula facebook/fb/idb-companion && brew install idb-companion` と `python3 -m pip install --user fb-idb`

## iOS版リリース手順

### ① バージョン更新（2箇所）

**1. `flutter/pubspec.yaml`**
```yaml
version: 2.3.0+7  # バージョン名+ビルド番号
```

**2. `flutter/ios/Runner.xcodeproj/project.pbxproj`**

以下の3箇所を変更（Runner の Profile / Debug / Release）:
```
MARKETING_VERSION = 2.3.0;      # X.Y.Z 部分（+N は含めない）
CURRENT_PROJECT_VERSION = 7;    # +N の数字
```

> ⚠️ `RunnerTests` の `MARKETING_VERSION = 1.0;` / `CURRENT_PROJECT_VERSION = 1;` は**変更しない**

### ② IPA ビルド

```bash
cd flutter
flutter build ipa --release
```

完了すると `build/ios/ipa/darias.ipa` が生成される（所要時間：数分）。

> ⚠️ Xcode の `Product → Archive → Distribute App` は使わない。
> 一部のパッケージ（`objective_c.framework` 等）にシミュレーター用 x86_64 スライスが混入し、
> App Store Connect へのアップロード時にエラーになるため。

### ③ App Store Connect にアップロード

**Mac App Store の「Transporter」アプリを使う（推奨）：**

1. Transporter を起動（未インストールの場合は Mac App Store からインストール）
2. `build/ios/ipa/darias.ipa` を Transporter にドラッグ＆ドロップ
3. 「配信」ボタンをクリック

**コマンドラインの場合：**

```bash
xcrun altool --upload-app --type ios \
  -f build/ios/ipa/darias.ipa \
  --apiKey <your_api_key> \
  --apiIssuer <your_issuer_id>
```

```bash
git add flutter/pubspec.yaml flutter/ios/Runner.xcodeproj/project.pbxproj
git commit -m "chore: バージョンをX.Y.Z+Nに更新"
git push origin main
```

```bash

```

生成物: `flutter/build/app/outputs/bundle/release/app-release.aab`（所要時間：数分）

### ②-2 Google Play Billing Library のバージョン確認（必須）

Google Play は **Billing Library 8.0.0 以降**を必須としており、**2026年8月31日**以降はこれを満たさないアプリのアップデートが承認されない。プラグインを更新した回、または久しぶりのAndroidリリース時は、ビルドしたAABに実際に含まれるバージョンを確認する。

```bash
cd flutter
unzip -p build/app/outputs/bundle/release/app-release.aab \
  BUNDLE-METADATA/com.android.tools.build.libraries/dependencies.pb | strings -a -n 3 | grep -A3 billing
# → com.android.billingclient / billing / 8.0.0  であればOK
```

- Billing のバージョンは `flutter/pubspec.yaml` の `in_app_purchase` が決める（`in_app_purchase` 3.3.0 → `in_app_purchase_android` 0.5.x → Billing 8.0.0）。Gradle側で直接指定はしていない。
- 詳細は [課金サービス仕様書 3-1](../architecture/課金サービス仕様書.md) を参照。

### ③ Google Play Console にアップロード

2. 「新しいリリースを作成」→ AABファイルをアップロード
3. リリースノートを入力して審査提出

> ⚠️ `versionCode`（+N の数字）は毎回 **必ず +1** すること。同じ versionCode は再アップロード不可。

### いつやるか（待ち時間に合わせる）

| タイミング | やること | 理由 |
|---|---|---|
| IPA をアップロードしたあとの処理待ち（15〜30分） | ① シミュレータで素材を撮る → ② ストア画像（iPhone・iPad）を生成して目視 → ③ App Store Connect に画像を登録 → 審査に提出 | ストア画像は審査に出す前に登録が必要。**ビルド中は撮影できない**（シミュレータでの起動もビルドを伴い、`flutter build ipa` と同じビルド用フォルダを取り合う）ため、ビルドが終わってから撮る |

## よくあるミス

| 症状 | 原因 | 対処 |
|-----|------|------|
| App Store Connect アップロード時に「Invalid architecture / x86_64」エラーが出る（Xcode Archive経由） | Xcode Archive 経由だと一部パッケージにシミュレーター用スライスが混入する | `flutter build ipa --release` で IPA を生成し Transporter でアップロードする |
| App Store Connect アップロード時に「Invalid executable. objective_c … x86_64 slice」エラーが出る（`flutter build ipa` でも発生） | `objective_c` パッケージの hooks_runner が x86_64 版 dylib をアーカイブに混入させる既知の問題 | 下記「objective_c x86_64 スライス修正手順」を参照 |
| Xcode が「file modified by another application」ダイアログを出す | `project.pbxproj` を外部ツールで編集した | **「Use Version on Disk」** を選択 |
| Web版のバージョンが反映されない | `flutter build web --release` を再実行せずにデプロイした | ビルドしてからデプロイ |

## objective_c x86_64 スライス修正手順

`flutter build ipa --release` 後に Transporter で「Invalid executable … x86_64 slice」が出た場合の対処。

```bash
ARCHIVE="flutter/build/ios/archive/Runner.xcarchive"
FRAMEWORK="$ARCHIVE/Products/Applications/Runner.app/Frameworks/objective_c.framework"
SIGN_ID="Apple Distribution: ryosuke onodera (UYP6X4YKVM)"
IPA_DIR="flutter/build/ios/ipa"

# arm64版 dylib（0b28f89409/ 配下）に差し替え
cp "flutter/.dart_tool/hooks_runner/shared/objective_c/build/0b28f89409/objective_c.dylib" \
   "$FRAMEWORK/objective_c"

# フレームワーク再署名
codesign --force --sign "$SIGN_ID" "$FRAMEWORK"

# IPA を元のパスに再エクスポート（上書き）
xcodebuild -exportArchive \
  -archivePath "$ARCHIVE" \
  -exportOptionsPlist "$IPA_DIR/ExportOptions.plist" \
  -exportPath "$IPA_DIR"
```

`flutter/build/ios/ipa/darias.ipa` を Transporter でアップロードする（ファイルは上書きされる）。

## Cloud Functions のデプロイ（関数変更時のみ）

**デプロイ漏れの確認手順は「リリース前チェック」の節を参照。**

```bash
# 特定の関数のみ（推奨。変更したファイルを使う関数だけ）
firebase deploy --only functions:classifyAndExtract --project my-character-app

# 全関数（内容が変わらない関数も再デプロイされ、全てコールドスタートし直す）
firebase deploy --only functions --project my-character-app
```

> `--only` を付けない `firebase deploy` は使わない。
> hosting の `darias-app` は `flutter/build/web` を配信しているため、
> **ローカルに残っている古いWebビルドがそのまま本番公開される。**
