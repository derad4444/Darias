## 全体の流れ

```
Cloud Scheduler  metrics-daily（毎朝 6:00 JST）
  └ POST /collect-metrics（reels-bot・X-Auto-Token で保護）

画面の「今すぐ集計」ボタン
  └ POST /collect-metrics-now（reels-bot・Firebase の ID トークンで運営者か確認）

        ↓ どちらも MetricsCollector.collect()（src/metrics/collector.py）

  App Store Connect / GA4 / AdMob / Instagram / Threads / Firebase Auth / Firestore（性格の分布）
        ↓
  Firestore admin_metrics/*（日別スナップショット）
        ↓
  darias-dashboard.web.app（Google ログイン → Firestore を直接読む）
```

- 収集元ごとに独立して動き、**1つが失敗しても他は保存する**。失敗は `admin_metrics/latest.errors` に残り、画面上部に「取得できなかったもの」として出る
- 同じ日に何度集計しても、その日の文書を上書きするだけ
- 「今すぐ集計」は直前の集計から2分以内は実行しない（`MIN_INTERVAL_SEC`）

| AdMob | `sources/admob.py` | 日別の推定収益（円）・表示・クリック・リクエスト | 初回は 2025-10-01 から、以降は直近7日を取り直す |
| Instagram | `sources/social.py` | フォロワー数・投稿数・前日のリーチ／表示／プロフィールのリンクのタップ／新しい60件の投稿の成績 | その日の値（過去の日別は API から取れないため、毎日記録して推移にする） |
| Threads | `sources/social.py` | フォロワー数・前日の表示／いいね／返信など・新しい120件の投稿の成績（1日8本投稿するため Instagram より多く取る） | 同上 |

### GA4 は日本のユーザーだけを数える

`country = Japan` で絞る。2026-08-19〜10-10 の新規 66 端末のうち約50端末は、
国も機種も不明な Android（Google Play の事前リリースレポートのテスト端末）と、米国の iPhone（Apple の審査端末）だった。
含めるとファネルが実態よりずっと悪く見える。

### ファネルの段階

| 段階 | 数え方 |
|---|---|
| 初回起動 | `first_open` |
| ホーム到達 | 画面 `main` |
| チャット送信 | `chat_message_sent` |
| 自分会議 | 画面 `meeting` |
| 課金画面 | `paywall_view` |
| 購入 | `purchase` |

イベント・画面の定義は [Analytics計測仕様書](./Analytics計測仕様書.md)。
直近30日のファネルは「期間内に各段階へ来た人数」なので、30日より前に初回起動した人も数え、上の段より多くなることがある。

### App Store のレポート

`analyticsReportRequests`（ONGOING、ID は `ASC_ANALYTICS_REQUEST_ID`）に対して Apple が作る日次ファイルのうち、次の3つを読む。
ファイルは gzip のタブ区切りで、**列は名前で読む**（並びが変わることがあるため）。

| レポート | 保存先のキー |
|---|---|
| App Store Discovery and Engagement Standard | `engagement` |
| App Downloads Standard | `downloads` |
| App Store Purchases Standard | `purchases` |

読み込んだファイルは `admin_metrics/state.ascProcessed`（`レポートキー:処理日`）に記録し、次回から読まない。
1回の集計で読むのは各レポート45ファイルまで（初回に過去分がまとめて届いても時間内に終わるように）。

### 性格の分布

DARIAS の性格の集計はここが唯一の場所。`collectionGroup("details")` で全キャラクターの `details/current` を読み
（数えるのに必要な `personalityKey` / `element` / `typeName` / `axisScores` だけを select する）、元素・タイプ名・性別・`personalityKey` ごとの人数を数える。

- 結果は `PersonalityStatsMetadata/summary` にも上書きする。自分会議の統計（`generateSixPersonMeeting.js` の `calculateStatsFromAnalysis`）が
  `total_completed_users` と `personality_counts` を読むので、この文書の形（[Firestoreスキーマ仕様書](../firebase/Firestoreスキーマ仕様書.md#personalitystatsmetadata)）は変えない
- `element` / `typeName` が保存されていない古い文書は `axisScores` から求める（`shared/functions/src/personality/axisCalculator.js` と同じ境界。collector 側の `determine_element` / `determine_type_name`）。判定の境界を変えたら両方を直す
- 「不明」の元素は画面で「未確定」と表示する（まだ元素が決まっていない赤ちゃん段階のキャラクター）
- キャラクター数は details を持つ全キャラクター。テスト用や削除済みアカウントのものを含むため、Firebase Auth の人数より多い
- 成長段階は `users/{uid}.growthStage`、バッジ診断の進み具合は `users/{uid}/personalityBadges/current.slots` の数を数える
  - バッジの文書には会話の本文（`active.turns`）も入っているため、**`slots` だけを select で読む**
  - 区分は `0` / `1-9` / `10-19` / `20`（`AnalyticsService.badgeBucket` と同じ）

## 画面

### 全体の作り
- 上部の帯に挨拶・最終更新（自動／手動）と「今すぐ集計」。その下に、スクロールしても残る**期間の切り替え**とタブ
- **期間**: 7日／30日（既定）／90日／全期間／期間を指定（開始日と終了日）。選んだ期間の数字と、その直前の同じ長さの期間（全期間のときは比較しない）を比べる
  - 日別に足し合わせられる数字（表示回数・ダウンロード・新規・収益など）は、日別の文書を期間で合計する
  - **ファネルは人数（重複を除いた数）なので日別に足せない**。7／30／90日／全期間は collector がそれぞれ取った値（`funnel7` / `funnel30` / `funnel90` / `funnelAll`）を出し、期間を指定したときは直近30日の値を出す（画面に注記する）
  - **使った人（重複なし）**も同じ理由で、collector が選択肢ごと（直前の同じ長さの期間も）に取った値（`activeUnique`）を出す。期間を指定したときは出さない。前の期間が計測開始（2026-08-19）より前にかかるときは比較しない
  - 投稿の成績は投稿日で絞り込む。レビュー一覧・月別の新規アカウント数・性格は期間に関係なくすべて（最新）を出す
- **大きな数字のカード**: 期間の合計（または最後の値）を大きく出し、前の期間との増減（▲▼と%、前の期間の値）と、期間内の小さな推移グラフを添える。数字は0から数え上げて表示する（OS の「視差効果を減らす」設定のときは動かさない）
- **良い結果・悪い結果で背景色を変える**。大きな数字のカードは、前の期間から5%以上増えたら緑、5%以上減ったら赤（`TONE_THRESHOLD`）。ハイライトは「いちばん伸びた数字」を緑、「いちばん落ちた数字」を赤にし、フォロワー（期間内の増減）と期間内のレビュー（平均★4以上で緑、★2.5以下で赤）も同じく色を付ける。色だけに頼らないよう、▲▼と%、ハイライトには「良い」「要注意」のラベルを必ず添える
- **すべての項目に「？」ボタン**。押すと「何の数字？」「どう見る？」の説明が出る（文言は `app.js` の `HELP`）
- データがまだ無い数字は「0」ではなく「–」と理由（「Apple のレポート待ち」「AdMob 未接続」など）を出す
- グラフはすべてホバー（タップ）で値が出る。各グラフの下の「表で見る」で同じ数字を表で見られる
- **表はすべて列名を押すと並べ替えられる**（もう一度押すと昇順・降順が入れ替わる）
- 最後に開いたタブと期間（日付の指定以外）はブラウザに覚えさせる（`localStorage`。保存できなくても動く）
- 検索エンジンに載せない（`noindex`。`firebase.json` のヘッダーと `<meta name="robots">`）

| アプリ内 | 新規・使った人（重複なし）のカード／新規とアクティブの日別推移／ファネル／週別の表 |

ファネルの「前の段からの割合」は、期間内に各段階へ来た人数どうしの割合。期間より前に始めた人が多いと100%を超えるので、そのときは割合を出さず「比べられません」と出す。

## アクセスの制限

**保護は Firestore ルールで行う。** 画面がログインしたアカウントを確かめているのは表示の出し分けにすぎず、
URL を知られても、運営者以外はデータを1件も読めない。

運営者は**メールではなく UID で判定する**。運営者のアカウントはメール・パスワードで登録したあとに Google ログインを連携しており、
`email_verified` が false のままのため、メールの確認状態を条件にすると本人も読めない。UID は1つのアカウントにしか付かないので、判定としても厳密。

```
match /admin_metrics/{rest=**} {
  allow read: if request.auth != null
              && request.auth.uid == 'l5M6D7XvjwSvC15HJYHFdKZo0bz1';
  allow write: if false;
}
```

| 入口 | 確認していること |
|---|---|
| `/collect-metrics` | `X-Auto-Token` が `AUTO_RUN_TOKEN` と一致（Cloud Scheduler 用） |
| `/collect-metrics-now` | Firebase の ID トークンを `verify_id_token` で検証し、UID が運営者のもの（`DASHBOARD_ADMIN_UID`）。CORS は `darias-dashboard.web.app` / `.firebaseapp.com` だけ |

保存するのは人数・回数・投稿の成績だけ。メールアドレス・名前・会話や日記の中身は保存しない
（月別の登録数は Firebase Auth の作成日時だけを数える）。

## Firestore のデータ構造

詳細は [Firestoreスキーマ仕様書](../firebase/Firestoreスキーマ仕様書.md) の `admin_metrics`。

| パス | 中身 |
|---|---|
| `admin_metrics/latest` | `startedAt` / `finishedAt` / `status` / `trigger`（`schedule` / `manual`）/ `sources`（収集元ごとの `ok` / `error`）/ `errors` |
| `admin_metrics/summary` | `funnel7` / `funnel30` / `funnel90` / `funnelAll` / `activeUnique`（`7` / `7prev` / `30` / `30prev` / `90` / `90prev` / `all`）/ `weekly` / `paywallSources` / `reviews` / `instagramPosts` / `threadsPosts` / `signupsByMonth` / `updatedAt` |
| `admin_metrics/daily/days/{YYYY-MM-DD}` | `date` / `appStore`（`engagement` / `downloads` / `purchases`）/ `ga4` / `admob` / `instagram` / `threads` |
| `admin_metrics/personality/days/{YYYY-MM-DD}` | `date` / `totalCharacters` / `uniqueTypes` / `elements` / `typeNames` / `gender` / `growthStages` / `badgeBuckets` |
| `admin_metrics/state` | `ascProcessed`（読み込み済みの App Store レポート）/ `admobBackfilled` |

日別の文書は収集元ごとに merge で書くので、ある日に取得に失敗した収集元の過去の値は消えない。

## 認証情報の置き場所

| 認証情報 | 置き場所 |
|---|---|
| App Store Connect API キー（`.p8`・Admin） | Secret Manager `asc-api-key` → Cloud Run の `/asc/AuthKey.p8`。ローカルの正本は `~/.appstoreconnect/private_keys/` |
| ASC の Issuer ID・キーID・App ID・レポート申請 ID | reels-bot の `env.yaml`（gitignore） |
| GA4 | 鍵なし。Cloud Run のサービスアカウントが `darias-analytics@my-character-app.iam.gserviceaccount.com`（GA4 プロパティ `488119158` の閲覧者）になりすます |
| AdMob | Secret Manager `admob-oauth`（client_id / client_secret / refresh_token の JSON）→ Cloud Run の `/admob/oauth.json`。AdMob API はサービスアカウント非対応のため、運営者の Google アカウントで1回許可して得たもの |
| Instagram / Threads | 自動投稿と同じ長期トークン（Storage `state/ig_token.json` / `state/threads_token.json`。月次で自動延長） |

## デプロイと運用

| 対象 | コマンド |
|---|---|
| 画面 | `firebase deploy --only hosting:darias-dashboard --project my-character-app`（DARIAS/ で実行） |
| Firestore ルール | `firebase deploy --only firestore:rules --project my-character-app` |
| collector | reels-bot を `gcloud run deploy reels-bot --source . --region asia-northeast1 --env-vars-file env.yaml --update-secrets /asc/AuthKey.p8=asc-api-key:latest,/admob/oauth.json=admob-oauth:latest` |

- Hosting サイト `darias-dashboard` は Firebase Auth の承認済みドメインに入れてある（入れないと Google ログインのポップアップが失敗する）
- Cloud Scheduler `metrics-daily`: `0 6 * * *` Asia/Tokyo、`/collect-metrics` に `X-Auto-Token` 付きで POST
- **TikTok は対象外**。再生数などを読むには権限（`video.list` など）の追加と再審査が必要

## 費用

- Cloud Run: 1日1回＋手動、1回あたり1分ほど。無料枠内
- Firestore: 1回の集計で書き込み数十件（日別の文書は GA4 を全期間取り直すため導入日からの日数分）。読み取りは画面を開いたときだけ。無料枠内
- 外部 API（App Store Connect・GA4 Data API・AdMob・Instagram・Threads）はいずれも無料
- Cloud Scheduler `metrics-daily`: 請求先アカウントの無料枠（3ジョブ）はすでに超えているため、1ジョブ月$0.10
- 性格の分布は1回の集計で全キャラクターの details を読む（2026-10 時点で約140件）
- Claude などの AI の呼び出しは無い
